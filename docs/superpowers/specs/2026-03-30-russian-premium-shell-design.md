# Russian Premium Shell Design

## 1. Контекст

Внутренние продуктовые страницы `Home`, `Lessons`, `Challenges`, `Playground`, `Analytics`, `Profile` уже приведены к сильному premium-визуальному языку. `Pricing` тоже находится на хорошем уровне и визуально ощущается как часть коммерческого продукта.

Проблема осталась во внешнем контуре:
- [Landing.tsx](/C:/Users/LXKLGNV/Новая%20папка/VibeStudy2/src/pages/Landing.tsx) содержит битую кириллицу и визуально уступает внутренним экранам;
- [Auth.tsx](/C:/Users/LXKLGNV/Новая%20папка/VibeStudy2/src/pages/Auth.tsx) работает, но по тону и качеству текста ощущается слабее продукта;
- [Privacy.tsx](/C:/Users/LXKLGNV/Новая%20папка/VibeStudy2/src/pages/Privacy.tsx), [Terms.tsx](/C:/Users/LXKLGNV/Новая%20папка/VibeStudy2/src/pages/Terms.tsx) и [Support.tsx](/C:/Users/LXKLGNV/Новая%20папка/VibeStudy2/src/pages/Support.tsx) выглядят как launch-draft страницы, а не как часть дорогого обучающего сервиса.

В результате путь `лендинг -> вход -> trust/legal -> pricing -> продукт` пока не ощущается единым.

## 2. Цель

Сделать весь внешний контур платформы полностью русскоязычным и довести его до того же premium-уровня, что и внутренние страницы продукта.

После завершения этого блока пользователь должен получать цельное впечатление:
- продукт с первого экрана выглядит дорогим и собранным;
- тексты читаются естественно на русском;
- legal/support страницы не выглядят как временные заглушки;
- вход ощущается частью продукта, а не техническим экраном.

В этот этап входят только следующие страницы:

- [Privacy.tsx](/C:/Users/LXKLGNV/Новая%20папка/VibeStudy2/src/pages/Privacy.tsx)

В этот этап не входят:
- переписывание внутренних учебных экранов;
- новый billing-провайдер;
- финальная юридическая вычитка юристом;
- полный mobile redesign всей платформы.

## 4. Продуктовое направление

Платформа должна быть целиком на русском языке.

Это не означает, что визуально продукт должен стать “локальным утилитарным сервисом”. Наоборот, задача в том, чтобы сохранить дорогой premium-характер:
- тёмная кинематографичная подача;
- аккуратные акценты;
- сильная типографика;
- ощущение продукта для амбициозного пользователя, а не для случайного трафика.

Тон коммуникации:
- дружелюбный;
- уверенный;
- без канцелярита;
- без дешёвого маркетингового крика;
- единый стиль обращения на `ты`.

## 5. Дизайн-принципы

### 5.1 Общие принципы

- Внешний контур должен визуально совпадать с качеством текущего `Pricing`.
- Не использовать битую кириллицу, смешение русских и английских CTA и случайные placeholder-формулировки.
- Не возвращать болотные или жёлто-зелёные акценты.
- Не использовать дешёвые outlined-кнопки как основной стиль CTA.
- Не разводить визуальные паттерны: кнопки, карточки, бейджи, фоновые градиенты и отступы должны быть согласованы между всеми внешними страницами.

### 5.2 Визуальный характер

Рекомендуемое направление:
- premium dark editorial;
- мягкие стеклянные и полупрозрачные поверхности;
- сильный hero и крупные заголовки;
- выразительные, но не перегруженные glow-акценты;
- читабельный русский текст без ощущения “переведённого интерфейса”.

### 5.3 UX-подход

Пользователь с первого экрана должен понимать:
- что это за продукт;
- кому он подходит;
- что произойдёт после входа;
- где посмотреть тарифы;
- где получить помощь;
- где найти юридическую информацию.

## 6. Требования по страницам

### 6.1 Лендинг

Лендинг должен:
- содержать сильный hero-блок полностью на русском;
- объяснять суть продукта коротко и без перегруза;
- показывать стартовые треки;
- показывать ключевые преимущества продукта;
- давать ясный путь в `Войти`, `Начать бесплатно`, `Тарифы`.

Требования к контенту:
- убрать битую кириллицу полностью;
- переписать блоки так, чтобы продукт продавался через ежедневный обучающий ритм, AI-помощь и честный прогресс;
- убрать ощущение draft-посадки.

Требования к UX:
- hero должен быстро давать ценность;
- CTA должны быть прозрачными;
- лендинг должен поддерживать trust-links в футере.

### 6.2 Auth

Экран входа должен:
- быть полностью на русском;
- визуально совпадать с остальным premium-контуром;
- поддерживать Google login и magic link;
- показывать понятные русские ошибки;
- иметь чистый success-state после отправки magic link.

Требования к UX:
- пользователь не должен чувствовать, что попал на “техническую форму”;
- legal links должны быть читаемы и встроены естественно;
- тексты о testing mode и ограничениях OAuth должны быть понятны.

### 6.3 Privacy

Страница политики должна:
- остаться launch-документом, но выглядеть как реальная trust-page;
- быть полностью на русском;
- объяснять, какие данные хранятся и зачем;
- быть визуально спокойной и доверительной.

Требования:
- убрать битую кириллицу;
- уйти от ощущения сухого placeholder-контента;
- сохранить заметку о том, что перед публичным запуском документ должен быть заменён финальной юридической версией.

### 6.4 Terms

Страница условий должна:
- быть полностью на русском;
- объяснять доступ, ограничения, модель использования и общие правила сервиса;
- визуально совпадать с `Privacy`.

Требования:
- убрать битую кириллицу;
- сохранить draft-характер только там, где это честно нужно для soft launch;
- не делать страницу визуально “канцелярской”.

### 6.5 Support

Страница поддержки должна:
- быть полностью на русском;
- давать один понятный канал связи;
- объяснять, с чем писать;
- объяснять, что приложить к сообщению.

Требования:
- визуально поднять страницу до уровня продукта;
- не делать её просто списком карточек без контекста;
- явно поддержать сценарии: вход, прогресс, AI, оплата.

## 7. Контентные требования

- Все пользовательские тексты в рамках этого блока должны быть на русском.
- Не должно быть битой кодировки.
- Не должно быть смешения английских и русских CTA.
- Не использовать машинный или канцелярский тон.
- На всех страницах использовать единый стиль обращения на `ты`.
- Не использовать фейковые юридические формулировки, выдавая их за финальные. Если текст draft, это должно быть обозначено честно.

## 8. Технические требования

- Не ломать существующую маршрутизацию.
- Не ломать текущий auth flow.
- Не ломать переходы на `Pricing`, `Privacy`, `Terms`, `Support`.
- Сохранить адаптивность на desktop и приемлемую работу на mobile.
- Не вносить регресс в уже сделанные premium-экраны.
- При необходимости можно обновить общие дизайн-токены и shared-стили, но без визуального отката текущих сильных страниц.

## 9. Проверка

После реализации должны проходить:
- `npm run lint`
- `npm run build`
- `npm run test:e2e`

Минимальная ручная проверка:
- `/`
- `/auth`
- `/privacy`
- `/terms`
- `/support`
- переходы между ними

## 10. Критерии приёмки

Работа считается принятой, когда:
- на всех пяти страницах нет битой кириллицы;
- вся платформа в этом контуре полностью на русском;
- лендинг, auth и trust-pages ощущаются как один premium-продукт;
- legal/support ссылки работают;
- нет пустых CTA или визуальных “черновых” блоков;
- внешний контур не уступает по качеству `Pricing`.

## 11. Следующий шаг после этого блока

После завершения внешнего контура логичным следующим этапом будет:
- mobile pass для ключевых экранов;
- финальный polish маршрута `лендинг -> auth -> pricing -> profile`;
- live billing-provider integration, когда будут готовы внешние merchant credentials.
